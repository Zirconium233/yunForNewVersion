# 方案复核与修订实施基线

日期：2026-09-11。评审对象为本地 APK 3.6.6 反编译源码和当前 Python 仓库。

本文件优先于 adaptation_plan.md、plan_2.1_refactor.md、plan_2.2_adaptation.md、plan_2.3_face.md 中冲突的实施结论。原文保留作为调查记录。此次只修订文档，不实现业务代码，不请求远程服务，不使用账号。

## 1. 结论

- 2.1 模块化重构可行，但依赖选型、兼容承诺和迁移范围过大，应分阶段收缩。
- 2.2 多数字段差异有静态依据，但包含已实现功能、错误默认值、遗漏的字段关联和未经证明的服务器行为。可做离线适配，不能承诺线上通过。
- 2.3 “一张自拍低成本通过”缺乏验证依据，不作为交付承诺。删除成功率、PAD 必然可过、embedding 距离等无实测结论。首期仅识别人脸要求并停止自动流程，提示用户通过官方 App 完成核验；人工接续另行验证。
- 全部完成不是几十行补丁：建议完整工程预算为业务代码 1,600–2,650 行、测试 600–1,000 行，合计约 2,200–3,650 行需要编写或实质修改的代码。大部分现有逻辑可搬迁，不能把新包最终行数都算作新增代码。
- 推荐下一轮先做范围封闭的 A 阶段（约 250–450 行业务修改 + 150–250 行测试）。如果下一轮要求一次完成重构、适配、学校配置与恢复机制，应按中等规模工作交给本地模型分阶段实现，再做复核。

## 2. 已核对的关键错误与修正

以下路径未加前缀时，Java 文件位于 work_dir/src/sources/com/yunzhi/tiyu/。行号对应评审时版本。

### 2.1 重构部分

1. **不要引入通用自动重试。** 原方案“信封接口幂等、重放安全”不成立：加密封装不能证明 start、finish、注册或分段上传幂等。读超时可能发生在服务器已提交之后。查询类接口经确认后才有限重试；状态改变请求遇到不确定结果，应保留现场、报告状态未知，待状态查询确认。
2. **先保留 requests。** 现有规模不需要同时切换 httpx、pydantic-settings、loguru、tenacity。使用 dataclasses、configparser、logging；pytest 作为开发依赖。迁移 HTTP 库与业务适配混在一起会扩大回归面。
3. **兼容真实 CLI。** main.py:120–126 的参数是 --config_path、--task_path、--auto_run、--drift，以及 -f/-t/-a/-d，不是原文中的连字符长参数。history.py 另有 --conf_path、--history_path。新拼法只能作为别名增加。
4. **不要承诺任意 from main import * 的动态全局兼容。** 导入到调用者的字符串等对象不会随模块变量重新赋值而自动更新。仓库内 history.py 应改为显式客户端注入；只对已知旧函数签名提供薄包装。旧全局如需保留，应明确是快照并限定支持方式。
5. **配置路径必须贯穿登录和写回。** tools/Login.py:19 仍读取 ./config.ini；tools/getUrl_Id.py 在模块导入时读取同名文件。重构时不能只改主入口而把多账号登录写回到默认配置。
6. **移除 chdir 前先定义路径契约。** main.py:10、history.py:3 有进程目录副作用；EasyAutoRunServer/run.sh 又依赖自己的相对配置路径。显式相对 CLI 路径按调用者工作目录解析，缺省资源按项目根目录解析；对仓库自带启动脚本同步验证，不应无声改变含义。
7. **不要首次启动自动迁移任务文件或创建软链接。** 保留 tasks_fch/tasks_txl/tasks_xc，通过路径映射读取即可。物理迁移收益很小，Windows 链接与旧脚本兼容会增加成本。

### 2.2 协议及运行流程

| 原结论 | 本地证据 | 修订要求 |
|---|---|---|
| 主脚本只复用固定 cipherKey | main.py:211–220 已有空配置生成随机 SM4 key，并始终调用 encrypt_sm2 | 保留已有能力，重点统一 Login/getUrl_Id 与主请求；不要重复开发 |
| APK 每个请求生成新 SM4 key | http/SMUtils.java:19–28 在单例初始化中创建 SM4；RetrofitService.java:51、101 使用已有对象 | 本样本显示共享 SM4 对象，每请求重新封装密钥；不能把“每次封装”写成“每次换钥” |
| 历史详情缺 gzip 解码 | history.py:168–185 已保存 key_ctx，进行 SM4 解密和 gzip 解压 | 将解码集中到客户端时，同时删除 history 的二次解码；这是重构而非全新功能 |
| 正常 finish 必加 recordEndTime | SportRunMapActivity.java:2593 仅 z2=true 时添加；所查 P1 调用在 1836/2609/2776/2810 都传 false | 不无条件添加；按已确认的调用分支构造，其他分支待查证 |
| finish/isStandard 同体各发一次即可 | 同文件 T1:2798–2810 → b0:481–514 → S1:2775；回调可能先上传尾批点，失败走另一分支 | 显式描述状态转换、尾批上传、业务失败与网络未知结果，不能忽略响应继续 finish |
| time 改名足够 | model/UpPointsModel.java:9–23，SportRunMapActivity.Y1:2939–2986 | times 是 long；StepNumber 是 int。runSteps、strides、speeds 与点序列存在关联，逐项核对单位、类型与零分母行为 |
| runStep 就是里程/步幅取整 | 同文件:4158 使用实际 stepNum；Y1 使用首尾累计步数差 | 里程反推步数不是 APK 原算法。样本读取应保留已有累计步数，缺失要显式标记，不能声称与真机一致 |
| 样本已有 runStep 因而已兼容 | main.py:508–518 重建 point_changed 时丢弃了 runStep | loader 到上传体的完整链路都要检查；仅检查 JSON 原文件不够 |

| BASE_URL 直接全局替换 | http/API.java:222 的 /api/ 是公共默认基址；实例化 RetrofitService 仍可传学校 host；main.py:193 直接拼接 host+router | 区分公共目录、学校业务服务、登录路由，统一 URL 边界避免重复或丢失 /api；不批量覆盖用户学校配置 |
| 旧 key/固定设备值仍被服务器接受 | 只有客户端代码，native key 来自 JNI | 客户端静态证据不能验证服务端接受情况，也未验证本版本 JNI 密钥值是否与仓库一致 |

补充限制：sysVersion、每请求 UUID 和 crsReocordInfo 的解压链有明确证据（RetrofitService.java:68–125）。Android 版本应来自统一设备配置，不能把示例 Android 14 变成强制值。“time 一直被服务端丢弃”“缺 isStandard 必判异常”“HTTP 模拟不受强更影响”“服务器不校验证书链”等表述均无服务器证据，应改为待验证假设。

### 2.3 人脸方案

- JTFaceCompareActivity.java:730–737 的请求体确有 faceBaseData、recordId，但字段少不能证明服务器没有图片检查、会话绑定或时序约束。
- 没检索到动作文案不等于完整证明无活体检查；FaceImageCompressor 还有反编译缺口。全库关键词搜索只能是线索。
- “小变换后 embedding 距离 <0.05”“视频帧天然通过静默 PAD”“真 PAD 概率低”均无模型、阈值和实测数据支持，应撤回。代码可以生成图像文件，并不等于核验可通过。
- faceTime 不能直接当作每隔多少秒触发一次：SportRunMapActivity.java:785–789 同时读取 faceTime 与 randomList；2990 起由 randomList 构造核验窗口；1477–1517 使用 faceTime 参与窗口倒计时。完整触发条件尚需继续追踪，不能按 faceTime±10% 编造调度。
- JTFaceCompareActivity.java:696–707 的 30 秒代码在上传等待界面中，不能直接写成“30 秒拍摄倒计时”。
- N 状态自动提交注册并轮询 Y 不是纯查询，可能涉及审核和既有底照。默认不自动注册或覆盖底照。
- 修订交付范围为 off/人工提示与本地状态建模；遇到需要核验的任务停止自动运行。官方 App 人工完成后能否继续同一 recordId，必须验证后才能实现 assist，不能把现有 mitmproxy 配置抓取脚本当作现成的会话接管功能。

## 3. 建议实施顺序

### A：小范围兼容基础（建议下一轮先做）

目标：建立可验证的客户端基础，不宣称完整跑步链路已适配。

1. 提取最小纯请求构造与响应解码边界，保留 requests 和现有加密实现；每请求上下文绑定 uuid、utc、key，避免并发串钥。
2. 统一主请求、登录、学校查询的头部构造及 URL 规则；设备版本从配置读取。保留旧 CLI，并传递实际配置路径。
3. 将历史详情解码统一到一处，支持明文 JSON、普通加密 JSON、加密 gzip JSON。HTTP 状态错误、解密错误、业务错误分别报告，禁止 except: 返回密文假装成功。
4. 添加超时，不为状态改变请求引入自动重试。日志及 dry-run 默认隐藏 token、密码、密钥、人脸数据。
5. dry-run 使用本地 fixture 及假传输，不登录、不探测学校、不调用地图服务、不 sleep、不改配置。dry-run 不允许构造函数隐式联网。
6. 首期识别人脸要求后停止；状态缺失或未知时不假设已通过。

验收：离线异常和成功解码测试通过；请求头签名上下文一致；任意工作目录下配置路径正确；history 不二次解密；旧 CLI 参数可解析；dry-run 所有传输均为假实现且不落敏感字段。加密黄金向量必须使用可确认的输入输出，不把随机 SM2 密文硬编码成固定快照。

### B：受控模块化重构

建立 yun/{config,crypto,api,track,runflow,history}.py 与 cli.py。会话数据先放 api 内 dataclass，不为少量字段另堆抽象。先迁移纯函数，再迁移配置和客户端，最后拆运行流程与交互。

保持现有任务 JSON 的只读兼容，测试空序列、单点、最后不足一批、非法数字、时间不单调和累计里程回退。轨迹算法先保持现状，另列缺陷，不把算法改造混入文件搬迁。用性质断言和关键样本测试替代大段随机轨迹快照。

### C：字段与状态流程适配

先建立字段映射表，包含来源、类型、单位、条件、空值策略、证据定位及“服务端未验证”标记，再实现状态转换。记录准备、已开始、上传中、待结束、已结束、状态未知等状态，逐项处理拒绝与尾批。

公共学校查询解析只根据已见模型和响应，不猜登录路由字段；保留显式配置覆盖，不在认证失败时跨多个服务器自动重放密码。预置校区仅用于任务目录选择，不宣称不同校区有不同认证实体。

### D：恢复机制，单独交付

持久化 recordId、当前批次、服务端确认位置与本地进度；原子写入；重启先查询服务端，再决定补传、继续或要求人工处理。仅存在 breakpoint 端点不等于恢复逻辑已实现。没有确认语义的请求不得盲目补发。

### E：线上验收，独立于代码完成

有可用测试条件后验证公共目录、学校地址、登录、只读详情，再验证实际运行状态转换。离线测试仅证明本地实现与已知证据一致，不能证明服务端接收或成绩有效。此次没有执行线上验收；人脸通过率不作估计。
